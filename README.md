# Bombadil Sandbox

A fully client-side playground for property-based UI testing. Run a small TodoMVC-style app, edit tests and application behaviors, and inspect the timeline or replay its steps.

Built for [Bombadil issue #231](https://github.com/antithesishq/bombadil/issues/231). This is a standalone prototype, not an official Bombadil distribution.

## Run it

The static build is included. With Node.js 22 or newer:

```sh
cd bombadil-sandbox
npm run dev
```

Open **http://127.0.0.1:4173**. No Rust installation or npm install is needed to serve the included build. It needs HTTP, not `file://`, to load its local assets.

The seven-step tour opens automatically on your first visit, after the app loads. Opening or dismissing it is remembered locally in your browser, so it stays closed on later visits. Use **Tour** in the top bar to reopen it. It introduces the example switcher, App and Tests editors, preview, reload icon, run controls, and failure reports without running steps or changing code, tests, or recorded history. Use Back/Next or the arrow keys to navigate; Escape or the close button exits. The tour adapts to mobile. When browser storage is unavailable, it remains available through the Tour button without auto-opening on every visit.

The preview’s top-right reload icon reopens the app from saved todos. A compact footer contains **Start over** and **Replay** as quiet actions, with **Continue** as the primary button. Continue appends random steps from the latest app state, preserving manual changes, saved todos, and test history; Replay reruns the recorded sequence and becomes Stop during execution. Reload app reopens saved state; Start over restores the initial todos and clears the timeline. All controls preserve your code edits, with descriptive tooltips. After the first step, a single scrubber selects recorded states, with a label such as “Step 3” beside it. Hover the label or scrubber for the action and total step count. Failures show just their cause in red below the scrubber. Stop keeps the recorded steps. Continue picks up from the current state; Replay starts the recorded sequence from the beginning.

Three persistent panes keep the **App** editor, **Tests** editor, and live preview visible together. The App editor contains a complete `createApp(storage)` module: initial state, save/load decisions, event handlers, filtering, counting, and the `view()` returned to the renderer. Tests contains the editable test for the chosen example. Editing it rechecks the recorded timeline without resetting the app or changing the selected state. Failures stop at the failing state. The preview contains the app, controls, result, and timeline scrubber, without a separate heading. The top-right Example switcher is the only dropdown; it chooses the app code and test together.

Both editors provide syntax highlighting, line numbers, wrapping, and Tab/Shift-Tab indentation. Press Escape then Tab to leave an editor using the keyboard. Drag the pane dividers or focus them and use the arrow keys to resize adjacent panes on desktop. The preview uses the available pane height, keeping its controls and timeline visible. Todo lists expand into that space and scroll only when they exceed it.

Failures explain the expected behavior and the observed result, such as “Selecting ‘Completed’ created a new unfinished todo. Filtering should only change which todos are shown.” Related todos are highlighted and identified by their text rather than internal IDs. Every failure also has an expandable **Bombadil report** generated by the unchanged upstream message renderer, including its failing formula, captured values, and timestamps. This also works for edited tests, whose short summary stays neutral instead of assuming the original lesson's meaning. All recorded states use the same markup and styling as the running app.

Behavior edits stay in a draft and leave Output untouched. Click **Apply changes** to replay the recorded steps with the edited code. Until then, manual interactions, Reload app, Continue, Replay, and Start over use the last applied behaviors. Start over preserves the draft; switching examples keeps each example's edits separately. Editing a test still rechecks the recorded history without rerunning the app. The module declares its own `todos`, `filter`, and `persist()` helper; nothing is injected as an undeclared variable. Add `persist();` inside `onToggle` after changing completion to fix the initial bug.

The top-right **Example** switcher offers six teaching exercises. Selecting one loads its behaviors and test and clears the timeline to the initial state. It waits for you to interact with the app or press **Continue**. Each exercise includes one intentional bug; **Apply changes** replays your recorded steps. The Tests pane shows the code directly. Applied code, unapplied behavior drafts, and test edits are kept separately for each example while the page stays open. The timeline starts fresh when switching. Start over preserves edits within the current exercise.

| Example            | What it teaches                                                   | Default failure step |
| ------------------ | ----------------------------------------------------------------- | -------------------- |
| Reload persistence | Capture an earlier state with `next` and compare it after reload. | 3                    |
| Items left         | An invariant counts every incomplete todo, including hidden rows. | 4                    |
| Filter visibility  | An invariant checks the exact visible list.                       | 5                    |
| Blank todos        | An invariant rejects empty and whitespace-only todo text.         | 6                    |
| Filter changes     | A transition keeps the items-left count unchanged when filtering. | 5                    |
| Adding todos       | A transition keeps the selected filter when adding an item.       | 7                    |

The five added exercises adapt `filtersCorrect`, `noBlankTodos`, `filterChangeDoesNotCreateItems`, and `addingItemPreservesFilter` from [Oskar Wickström's TodoMVC specification](https://github.com/owickstrom/bombadil-playground/blob/73202e6269b06cbf945c5a4735ca9fa47c4c7ab0/todomvc/todomvc.ts). The formulas use this playground's fixed DOM observations. The new transition tests use `next(...).implies(...)`: when the selected filter changes, preserve the count; when the total list grows, preserve the filter. These state-based guards also work in exported native specifications. The persistence exercise is the existing local example. Editing, toggle-all, and pluralization exercises would need more editable UI behavior and observations, so they are not included.

Each Continue burst stops at the first test failure or seven new steps. Click Continue again to explore further from the latest state while keeping the history. Replay and Apply changes still replay all recorded steps. Automatic runs also retain a 60-second time limit.

Each example has a default random seed chosen to reveal its first defect between steps 3 and 7 when you press **Continue**. The preceding steps change the app state, with a mix of actions before the failure. The guided sequences follow the same pace. Reload persistence retains seed 8: add, toggle, reload exposes the unpersisted completion change in three steps. The action generator is the same for every example and includes empty and whitespace-only submissions. These are seeded random choices; custom seeds explore other paths.

The latest output state is interactive: add, toggle, delete, or filter todos directly. Every step runs the last applied behaviors, checks the selected test, and appends to the timeline; **Replay** reproduces your manual sequence. **Reload app** tests saved state, and **Start over** clears the timeline back to the initial todos while keeping your code edits. Manual interaction is unavailable while steps are running or a test has failed. Earlier states are read-only; **Back to latest** returns to the latest state before you can continue randomly.

## App module boundary

`createApp(storage)` receives one explicit adapter: `storage.load()` returns a cloned saved value (initially `null`), and `storage.save(value)` stores a clone. The module decides what to save and when; the default saves the todos, not the active filter. Reload recreates the module from saved data. Start over clears storage and recreates the module from the initial state defined in your applied code.

The factory returns synchronous `onAdd(text)`, `onToggle(id)`, `onDelete(id)`, `onFilter(value)`, and `view()` functions. Its closure stays alive between steps, so ordinary local state works. `view()` returns `{ todos, visibleIds, remaining, filter }`. The renderer draws those values as given—it does not compute visibility or correct the count. The sandbox validates only the fixed Todo UI's data shape and bounds.

Tests read actual DOM rows, visibility, the displayed count, and the selected filter after rendering. Historical Output reproduces those observations, including incorrect counts or visibility. The filter test checks both the requested filter and the exact visible list, so hiding everything cannot pass accidentally.

Rendering, DOM event dispatch, storage transport, sandbox limits, and timeline recording remain playground infrastructure. No HTML/CSS panes are added.

## Build from source

Requires Node.js 22+, Rust stable (edition 2024), and its WebAssembly target:

```sh
rustup target add wasm32-unknown-unknown
npm ci
npm run build
```

The build compiles the Rust bridge and bundles the browser code. `dist/` is a self-contained static artifact and can be served under a subpath. No backend, CDN, account, or third-party runtime requests are required. The Publish Sandbox workflow builds and publishes `dist/` to GitHub Pages on each push to `main`. The checks workflow runs separately.

## What is real Bombadil here?

The evaluator is the unchanged upstream **`bombadil-ltl` Rust source**, compiled to WebAssembly, at commit `b8bc4a658abc5933c84d1afb9fff1ce24e05520f` (0.7.5). The TypeScript formula constructors, extractor cells, and access tracking are also vendored unchanged. See [vendor/README.md](vendor/README.md) and the upstream MIT license.

The browser adapter connects JavaScript closures to the Rust evaluator. It preserves closures across `next`, tracks captured observations for explanations, and steps temporal formulas using recorded elapsed milliseconds. It supports `always`, `now`, `next`, `eventually`, `.within()`, `.and()`, `.or()`, `.implies()`, and `not()` for the supplied DOM observations. Unknown formula values fail explicitly.

The action driver and seeded selection are specific to this example. They support add, toggle, delete, filter, wait, and reload. They are not the native Chrome driver and do not provide native input fidelity, arbitrary-site automation, network instrumentation, or coverage feedback. A seed controls choices in this example; it is not a native Bombadil seed. Replay uses concrete recorded actions.

The app itself is a small original TodoMVC-style teaching fixture, rather than a vendored TodoMVC framework implementation. Its app module runs in a persistent, time-bounded worker, and its render/settle boundary is intentionally simple. The standalone `todomvc.html` version uses real localStorage; the sandboxed playground uses a per-run storage bridge with the same save/reload behavior.

## Architecture

```text
Playground shell — editors, immutable history, revisions, controls
  ├─ opaque-origin evaluation frame
  │    └─ worker: upstream TypeScript API → bridge → Rust/WASM evaluator
  └─ opaque-origin application frame
       ├─ real DOM controls → DOM observations
       └─ bounded worker for the edited behavior module
```

Editable code has no access to the shell's DOM or storage. Frames have restrictive CSP, no same-origin permission, and no network access. The shell validates message sources. Property execution has a timeout; rebuilding its frame terminates the worker. Behavior execution is terminated after 700 ms. This is an instructional sandbox, not a service for executing adversarial uploaded applications.

Extractors are fixed in version one. They provide `todos`, `visible`, `remaining`, `filter`, `ready`, and `lastAction` cells. The Tests editor accepts JavaScript expressions; App accepts a JavaScript `createApp(storage)` factory. Neither supports TypeScript-only syntax or imports.

Editing a test creates a fresh evaluator for that example's test only and rechecks recorded observations; other examples' tests are not executed. Applying behavior changes resets and reexecutes recorded actions against the edited code; typing alone does not execute or stop the app. Historical views are read-only projections of recorded DOM observations, with scrollable todo lists; the current app remains at the end of the trace. Replay divergence is reported instead of silently replacing unavailable actions.

A failed test shows its cause in one message. Other results use **Test passed**, **Test pending**, or **No failure so far**. An unbounded invariant is never presented as proven: **No failure so far** only describes the recorded states. Pending temporal obligations remain pending at the end of a finite history.

## Validation

```sh
npm run build
npm run typecheck
cargo test --locked -p bombadil-sandbox-runtime
npm test

# In another terminal, with the static server running:
npm run test:browser
```

Browser checks use installed Google Chrome on macOS. CI uses Playwright Chromium. They exercise the defect, fix, history, source edits, errors, execution limits, mobile layout, and absence of external runtime requests. Screenshots go to `test-results/` (ignored).

The Node checks instantiate the actual WASM binary and cover closure capture, before/after diagnostic values, native violation reports, bounds, negation, errors, and reevaluation. Rust tests exercise the native evaluator adapter. These are targeted checks, not a claim of exhaustive compatibility with every Bombadil API.

For a native end-to-end comparison, install the official Bombadil **0.7.5** executable and run:

```sh
BOMBADIL_BIN=/path/to/bombadil npm run test:native
```

This runs native Bombadil against `todomvc.html`, using `tests/native.spec.ts` and real localStorage. The buggy app must fail the `persistence` property after reload; the fixed app must complete without violations. Native traces are retained in separately created temporary directories and their locations are printed. The native test is also included in CI.

## Export and integration

Advanced controls remain available from the browser console through `window.bombadilSandbox`: `run(seed, {create, interact, reload})`, `runGuided()`, `selectExample(name)`, `replay()`, `pause()`, `reset()`, `getState()`, `exportTrace()`, and `exportSpec()`. The guided flow follows the selected example. Omitting the run arguments uses the selected example's default seed and current weights. Reload the browser page to restore all initial edits.

**Playground trace JSON is not native `--reproduce` input.** The exported specification contains only the selected test and targets the selectors in the supplied standalone app; serve `dist/todomvc.html` and run it with the native CLI. Copy that file along with the specification when sharing the example.

There is an optional, feature-detected WebMCP surface: `read_playground_state` and `run_guided_example`. Both accept an empty object. The latter uses the selected example's sequence, last applied behaviors, and selected test. Browsers without WebMCP continue normally.

The tool contracts are exercised with a mock registry in browser tests. A browser providing the actual proposed WebMCP API was not available for validation.

See [IMPLEMENTATION-PLAN.md](IMPLEMENTATION-PLAN.md) for the original phased plan. This prototype is ready for local review. Integration into the upstream manual, unrestricted extractor editing, arbitrary generator code, and automatic counterexample shrinking remain follow-up work.
